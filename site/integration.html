Read the usage data from another app

Foxy Switcher runs a tiny HTTP daemon on 127.0.0.1. Every number you see in the app — each account's 5-hour, 7-day Opus and 7-day Sonnet usage, the reset countdowns, which account is currently in use — is served over that local API. Any program on the same machine can read it. No SDK, no API key, no auth.

Under the hood the daemon polls Anthropic's GET https://api.anthropic.com/api/oauth/usage endpoint for each pooled account, stores the result in a local SQLite database, and re-serves it. You don't talk to Anthropic — you talk to the daemon. It's three steps: find the port, pull the data, pick the account.

1. Find the port

The daemon binds a random port on 127.0.0.1 and writes it, atomically, to a plain-text file in its data directory: 

~/.foxy-switcher/port

The file holds a single number (e.g. 49153). Read it every time you make a request — the port can change across restarts, so don't cache it. If the file is missing, the daemon isn't running. The data directory can be relocated with the FOXY_DATA_DIR environment variable (or the daemon's --data-dir flag); if you've done that, read the port file from there instead.

2. Pull the usage data

With the port in hand, GET the account list: 

GET http://127.0.0.1:{port}/api/accounts

No authentication — the server only listens on 127.0.0.1, so it trusts anything already running on your machine. The response is a JSON object with an accounts array; each entry carries the three usage windows plus identity and lease metadata: 

{
  "accounts": [
    {
      "id": 1,
      "email": "you@example.com",
      "plan": "Claude Max 20x",
      "rate_limit_tier": "default_claude_max_20x",
      "status": "active",
      "five_hour":        { "utilization": 42, "resets_at": "2026-05-27T08:20:00.868404+00:00" },
      "seven_day":        { "utilization": 5,  "resets_at": "2026-06-03T02:00:00.868427+00:00" },
      "seven_day_sonnet": { "utilization": 0,  "resets_at": "2026-06-03T02:00:00.868436+00:00" },
      "usage_fetched_at": 1779867387977,
      "five_hour_threshold": 95,
      "seven_day_threshold": 95,
      "seven_day_sonnet_threshold": 95,
      "lease": { "device_id": "…", "device_name": "…", "mine": true,
                 "acquired_at": 1779866008571, "expires_at": 1779867607434 }
    }
  ]
}

The fields you'll most likely want, per account:

FieldMeaning
email / plan Account identity and its subscription label (e.g. “Claude Max 20x”).
rate_limit_tier Tier string such as default_claude_max_20x / default_claude_max_5x.
five_hour The 5-hour rolling window: { utilization, resets_at }.
seven_day The 7-day Opus window (shown as “7d Opus” in the UI).
seven_day_sonnet The 7-day Sonnet window.
utilization A percentage on a 0–100 scale (not a 0–1 ratio). 42 means 42%.
resets_at RFC 3339 timestamp when that window's usage resets to zero.
*_threshold The skip threshold for each window (default 95) — Foxy stops handing out an account once it crosses this.
usage_fetched_at Unix milliseconds of the last successful poll. Useful for staleness checks.
lease Who currently holds this account (vault mode). lease.mine is true if this device holds it — see step 3.

There's also GET /api/dashboard for pool-wide aggregates (cooling-account count, next reset time, peak utilization, a 24-hour hourly trend) if you want a single summary number instead of per-account detail.

3. Which account is “in use”?

The app marks one account as in use — the one Foxy Switcher is currently handing to Claude Code. To reproduce that flag, ask the credential-status endpoint: 

GET http://127.0.0.1:{port}/api/cred/status

{ "managed_account_id": 1, "native_backup_present": true, "injected_at": 1779865969297 }

Then look up managed_account_id in the /api/accounts array. This is exactly what the app's own UI does, and it's the right signal in both run modes:

  • Local mode (the default desktop app): managed_account_id is the account whose credentials are currently injected into Claude's config — the genuinely active one. There are no leases in this mode, so lease.mine stays false.
  • Vault mode (a shared self-hosted pool): there's no local injection, so the daemon falls back to the lease this device holds — managed_account_id then equals the leased account.
Don't key off lease.mine alone. It only means anything in vault mode; in local mode it's always false and you'd never find the active account. Always go through /api/cred/status → managed_account_id.

Copy-paste examples

Shell (curl + jq) — all accounts

PORT=$(cat ~/.foxy-switcher/port)
curl -fsS "http://127.0.0.1:$PORT/api/accounts" \
  | jq -r '.accounts[]
      | "\(.email) [\(.plan)]  5h=\(.five_hour.utilization)%"
      + "  7dOpus=\(.seven_day.utilization)%"
      + "  7dSonnet=\(.seven_day_sonnet.utilization)%"'

Shell — just the account currently in use

PORT=$(cat ~/.foxy-switcher/port)
BASE="http://127.0.0.1:$PORT"
MID=$(curl -fsS "$BASE/api/cred/status" | jq -r '.managed_account_id')
curl -fsS --max-time 15 "$BASE/api/accounts" \
  | jq --argjson mid "$MID" '.accounts[] | select(.id == $mid)
      | { email, plan,
          five_hour: .five_hour.utilization,
          seven_day_opus: .seven_day.utilization,
          seven_day_sonnet: .seven_day_sonnet.utilization }'

Node (zero dependencies)

import { readFileSync } from 'node:fs';
import { homedir } from 'node:os';

const base = `http://127.0.0.1:${readFileSync(`${homedir()}/.foxy-switcher/port`, 'utf8').trim()}`;

const { managed_account_id } = await (await fetch(`${base}/api/cred/status`)).json();
const { accounts } = await (await fetch(`${base}/api/accounts`)).json();

const inUse = accounts.find((a) => a.id === managed_account_id);
console.log(inUse.email, {
  fiveHour: inUse.five_hour.utilization,       // 0–100
  sevenDayOpus: inUse.seven_day.utilization,
  sevenDaySonnet: inUse.seven_day_sonnet.utilization,
});

Caveats & gotchas

  • The port changes. It's random per launch — re-read ~/.foxy-switcher/port on every poll instead of caching it.
  • utilization is 0–100, not 0–1. A value of 42 means 42%. Don't write a threshold like >= 0.9 expecting a ratio — that would fire at 0.9%.
  • No authentication. The API trusts every local process because it only binds 127.0.0.1. If you ever want a non-local app to read it, put your own authenticated proxy in front — don't expose the daemon's port directly.
  • /api/accounts can be slow. Building each account's lease view can take a few seconds, especially against a remote vault. Use a generous timeout (≥ 8 s) and cache the result locally; the daemon only refreshes usage about once a minute anyway, so polling faster than that buys nothing. /api/cred/status is cheap and returns instantly.
